# Import-accuracy benchmark

Measures how well a released `codemap` binary recovers file-to-file import edges, against truth produced by each language's own toolchain. One command, pinned inputs, full census, pre-registered repositories.

```bash
make bench            # downloads and verifies codemap v4.6.4, clones, builds truth, runs codemap, scores
bench/run.sh --group held_out
bench/run.sh --repo expressjs__express
CODEMAP=./codemap bench/run.sh      # score a local build against the same truth
```

Results land in `bench/results/v<version>.md` and `.json` (committed). Clones, virtualenvs, the downloaded binary and per-repo edge files live in `bench/cache/` and `bench/results/<version>/` (gitignored).

## What is measured

An **edge** is `source file -> target file`, both in the repository, both source files of the language under test, written as repository-relative paths with forward slashes. For each repository the benchmark builds two edge sets over the same universe of source files, then counts:

- **recall** = truth edges codemap also reports, over all truth edges
- **precision** = codemap edges that are in truth, over all codemap edges
- **95% intervals** are Wilson score intervals on the full edge census. There is no sampling; `n` is the number of edges in each set. Per-language pooled rows sum counts across the group's repos.

Scope rules are applied identically to both sides by `bench/score.py`: both the source and the target must be in the truth generator's file universe (the files the toolchain itself considers part of the build), and the target must carry the language's target extensions (`.go`; `.py`; for TypeScript and JavaScript any of `.ts .tsx .mts .cts .js .jsx .mjs .cjs`, never `.d.ts`, never under `node_modules`). Externals (standard library, third-party packages, Node builtins) are not edges on either side.

## How truth is built

Never a regex. Each generator writes `truth.edges` (`src<TAB>dst` lines), `truth.edges.files` (the source universe) and `truth.edges.meta.json`.

| language | truth | scope decisions |
|---|---|---|
| Go | `go list -e -json -deps ./...` with `GOFLAGS=-mod=mod GOWORK=off` for the package table and file universe, plus `go/parser` (ImportsOnly, `bench/truth/goimports`) for each file's own import declarations (`bench/truth/go.py`) | Go imports name packages. If file F declares an import of in-module package Q, F gets an edge to every non-test file of Q. Test files are out of scope on both sides because `go list` without `-test` reports no test imports. Files excluded by build constraints at the default GOOS/GOARCH are not in `GoFiles`, so they are out of scope as sources and as targets. An earlier draft fanned out from the package's union of imports, which gave files edges for packages they do not import themselves; it was replaced before any result was recorded. |
| TypeScript | TypeScript compiler API 5.9.3, `ts.resolveModuleName` with each `tsconfig.json`'s own options (`moduleResolution`, `paths`, `baseUrl`, `rootDirs`, `extends`), per package in monorepos (`bench/truth/ts.mjs`) | Sources are the files listed by some tsconfig in the repo (outside `node_modules`), excluding `.d.ts`. Specifiers come from import declarations, `export ... from`, `import x = require()`, `require("literal")` and `import("literal")`. Type-only imports count. Triple-slash references do not. A workspace package reached through a `node_modules` symlink is resolved to its real in-repo path. Dependencies are installed from the repo's lockfile with scripts disabled before resolution (npm, pnpm, yarn 1, yarn berry with the node-modules linker, or bun, as the lockfile says; pnpm and yarn are fetched from the npm registry at the version `packageManager` names, since corepack's own download path is blocked on some networks). A repo whose install fails is still resolved, without `node_modules`, and `install.json` says so. |
| JavaScript | Node 22's own resolver (`bench/truth/js.mjs`): `require.resolve` through `createRequire(file)` for CommonJS, `import.meta.resolve(spec, parentURL)` for ESM (needs `--experimental-import-meta-resolve`). Specifiers are extracted by the TypeScript parser in JS mode. | A file's module type is what Node uses: `.mjs` ESM, `.cjs` CommonJS, `.js` by the nearest `package.json` `"type"`. Sources are all in-repo `.js .mjs .cjs .jsx` files outside `node_modules`, `dist`, `build`, `vendor`, `coverage`. Resolutions to `.json` or to builtins are out of scope. Dependencies installed as for TypeScript. |
| Python | A virtualenv with the repo installed as documented (`pip install -e .`, falling back to `--no-deps`; an application that is not a package at all still resolves, from the repo root), then `ast` to walk import statements and `importlib.util.find_spec` inside that interpreter (`bench/truth/py_walk.py`), with the search order the interpreter gives the repository: the repo root first on `sys.path` (what `python -m pytest` and `python -m <module>` from the checkout provide, so `from tests.conftest import x` resolves), then the virtualenv. A file outside every package can only run as a script, and a script's own directory is `sys.path[0]` when it runs, so for such files a name is looked up in that directory first (`from common import x` beside `common.py`). | Sources are all in-repo `.py` files outside build, dist, venvs and site-packages. The target is the final module a statement names: `import a.b.c` -> `a/b/c.py` or `a/b/c/__init__.py`; `from a.b import c` -> `a/b/c.py` when `a.b.c` is a module, else `a/b/__init__.py` or `a/b.py`. Relative imports resolve against the file's package (directories containing `__init__.py`). Parent packages Python also executes on the way are not edges. Imports inside functions, `try` blocks and `if TYPE_CHECKING:` count: they are import statements. Namespace packages without `__init__.py` are not handled. |

## C, C++ and Rust (added for v4.7.1)

The same edge definition applies: `source file -> target file`, both in the repository, both in the truth generator's universe, counted once per ordered pair. The universe and the edges come only from the toolchain, and the scope rules below are applied to codemap's output by `bench/score.py` exactly as to the truth.

| language | truth generator | universe and edges |
|---|---|---|
| C and C++ | `cmake -S . -B <cache>/build -DCMAKE_EXPORT_COMPILE_COMMANDS=ON` with the repository's default options and clang as the compiler (`CC=clang CXX=clang++`, clang 18), then, for every translation unit in `compile_commands.json`, the unit's own command rerun with `-fsyntax-only -H -w` so the preprocessor prints the include tree it actually followed (`bench/truth/cc.py`). `bear` is not available in this environment, so repositories without a root `CMakeLists.txt` were excluded at selection rather than built with make. | Universe: every in-repo file that is a translation unit in `compile_commands.json` or appears anywhere in one of their include trees, excluding the cmake build directory (generated headers are not source). Edges: for each file in a tree, the files it directly includes at the depth below it (depth-1 lines are the unit's own includes, a depth-n line's parent is the nearest preceding depth n-1 line). A unit compiled several times (different flags or targets) contributes the union. System and third-party headers outside the repo are not edges. An include guarded by a condition the configuration leaves false is not in truth. A unit whose preprocessing stops at a missing header (a dependency this environment lacks) contributes the includes seen before the error and is counted in the run's metadata. |
| Rust | `cargo metadata` for the workspace, `cargo check --workspace --all-targets` for rustc's dep-info (`target/debug/deps/*.d`, the files rustc actually read per crate target), and rust-analyzer (the `rust-analyzer` rustup component, run as a language server) for resolution (`bench/truth/rust_la.py`). The references to resolve are listed per file by `bench/truth/rustsyn`, a small program on the `syn` parser (the Rust ecosystem's standard parser; never a regex): `mod name;` declarations, `use` tree leaves, multi-segment paths in expressions and types, and `include!`, `include_str!`, `include_bytes!` literals. | Universe: every `.rs` file named in the dep-info of a workspace member's target (a module behind a `cfg` the check leaves false is not in it). Edges: for each `mod name;` the file rust-analyzer's definition of `name` lands in; for each `use` leaf and multi-segment path, the file holding the definition of its last named segment (the segment before `*` for a glob), when rust-analyzer resolves it to a file in the repository; for `include!`-family macros, the literal resolved relative to the file, when rustc's dep-info lists that file. Paths into external crates, the standard library and the registry are not edges. Items re-exported with `pub use` resolve to the file that defines them, not to the re-exporting module; codemap resolves to the module named by the path, which the spot check classifies as scope ambiguity where the two differ. Inline `mod name { }` blocks produce no edge. |

Target extensions for scope: C and C++ any of `.c .cc .cpp .cxx .h .hh .hpp .hxx .inc .inl .ipp .tcc`; Rust `.rs`. Both endpoints must be in the universe.

## How codemap's edges are collected

codemap v4.6.4's `--deps --json` carries raw import strings, not resolved targets, so it cannot be scored. The resolved graph is exposed on two public surfaces, and `bench/codemap_edges.py` supports both:

- **daemon** (the method the results use): `codemap --watch .` from the clone root runs codemap's file-watcher daemon in the foreground; it builds the dependency graph once and publishes it to the daemon state file that codemap's own hooks and MCP server read, whose `imports` map lists, per file, the in-repo files it resolves to. The collector waits for the graph to be published and stable, copies the edges, and stops the daemon. (`codemap watch start` spawns the same daemon but gives up after a 30 second readiness wait and kills it on repositories whose initial scan takes longer, which gstack's 2,605 TypeScript files did; the foreground form is used for every repository.)
- **per-file** (the cross-check): `codemap --json --importers <file>` for every source file in the truth universe; its `imports` array is the same resolved list. Each call rescans the repository, which cost 13 to 20 seconds per file on these repos.

The two methods were run on all three held-out Go repositories and produced identical edge sets (ollama 7,230 edges, caveman 1,941, frp 2,969; zero differences in either direction), which is why the remaining repositories use the daemon. `bench/run.sh --method per-file` reruns the cross-check.

Both methods run with default configuration: no `.codemap/config.json` is written or tuned by the benchmark. codemap itself auto-writes one on first run in a git checkout, which is the behaviour a new user gets, and the runner leaves it alone. Its auto-detected `only` list can exclude files codemap would otherwise scan; the results report the not-indexed counts rather than correct for them.

The binary is the released asset, as a new user would install it: `codemap-full_<version>_linux_amd64.tar.gz` downloaded from the GitHub release and verified against the release's `checksums.txt` before use. The `-full` asset bundles the ast-grep the release was built against; the plain asset expects ast-grep on `PATH`.

## Spot check

`bench/score.py` draws five disagreeing edges per language (seed 20261103, mixing false negatives and false positives) from the held-out pool and lists them at the end of `results/v<version>.md`. Each is classified by hand in `results/v<version>-spotcheck.md` (with `bench/spotcheck.py` printing the evidence for one edge: the import line, universe membership, codemap's auto config and codemap's own `--importers` answer) as **codemap wrong**, **truth wrong** or **scope ambiguity**, with the reason, so a reader can judge whether the truth generators are themselves trustworthy. When a spot check shows a generator is wrong, the generator is fixed and the run is repeated; codemap is never changed to improve its score.

**Generator fixes made after seeing results (disclosed).** The first scored run resolved Python with only the virtualenv on `sys.path` (plus the repo root for repos that were not pip-installable). Its spot check showed truth missing edges the interpreter does make: `from tests.conftest import x` in test files (the repo root is on `sys.path` under `python -m pytest`) and `from common import x` in standalone scripts (the script's directory is `sys.path[0]`). The generator was changed to model both, as described in the table above, and every Python repository was rerun. The change raised codemap's Python precision; it was made because the interpreter resolves those statements, not because codemap does. The earlier numbers are in the PR description for comparison.

## Tool versions

Recorded in each run's `truth.edges.meta.json` and in the results JSON: Go, Node, TypeScript, Python and codemap versions. The run that produced `results/v4.6.4.md` used Go 1.24.7, Node v22.22.0 (npm 10), TypeScript 5.9.3, Python 3.13.16, ast-grep 0.42.1 (bundled in the release asset), and for dependency installs bun 1.4.2, pnpm 12.4.1, yarn 1.22.22 and `@yarnpkg/cli-dist` 4.9.2 as each repository's lockfile and `packageManager` field required.

## Limitations

- Linux amd64 only (the release asset the runner downloads).
- Go truth uses the default build tags; platform-specific files for other OSes are out of scope rather than counted against codemap.
- TypeScript sources are limited to files some tsconfig includes; scripts outside every tsconfig are not scored.
- JavaScript dynamic imports with non-literal specifiers are not edges on either side.
- Python truth models two invocation conventions (repo root on `sys.path`, script directory for files outside any package) besides the installed package. Code that extends `sys.path` at runtime (plugin loaders that add an extension directory, for example) is not modelled; its sibling imports are unresolvable in truth, and a codemap edge for them counts as a false positive. The spot check is where such cases are classified.
- codemap's ast-grep scan has a fixed 30 second budget per repository (not configurable in v4.6.4). When it runs out, the daemon reports a failed graph; such a repo is scored as zero codemap edges, labelled with the reason, rather than dropped.
- Truth reflects the toolchain's view at the default configuration. A repo whose build depends on code generation that was not run will have unresolvable specifiers; those are not edges in truth, and a codemap edge to a checked-in file with the same name would count as a false positive. The spot check is where such cases are classified.
- The benchmark reports wall time but does not benchmark speed; the per-file cross-check rebuilds codemap's graph on every call.
